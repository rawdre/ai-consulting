🛠️ The Workflow
How we start every website
The same seven steps on every build, in the same order. Following it is what makes the sites consistent — and what stops us rediscovering the same mistakes on each new project.
01

Name the one job

Before any design, write down the single action the site exists to cause. Not "a nice website" — one measurable action.

  • RAW Tennis Club → open a WhatsApp conversation
  • Top Imobiliária → get an enquiry on a specific property
  • Where does the traffic come from today, and what does it currently hit?
Gate: if you cannot name the action in one sentence, do not open a code editor.
02

Collect the facts before the design

Prices, hours, address, phone, real photos, the owner's own words. Anything not confirmed gets marked PENDING — never invented.

  • Lift the headline from what the client already says — they have a voice, don't invent one
  • Ask for originals off the phone, not screenshots or Instagram downloads
  • Get written consent for any recognisable person, especially children
Gate: a wrong price on a live site starts an argument at the first meeting. PENDING is always safer than a guess.
03

One config file = one source of truth

Every fact the site renders lives in a single config file. Components never hardcode business data, so the whole site can be corrected without opening a component.

  • Facts in one file (prices, ids, image paths) — words in another when the site is bilingual
  • Join them by id, so a price is written once and cannot disagree with itself
  • A PENDING value degrades in the UI to "ask us" — the site ships before every answer exists
04

Build the conversion path first

The button that causes the one job gets built and tested before anything decorative. Everything else is supporting cast.

  • Render a real, working link — never one that only becomes valid on click
  • Carry context into the message so the first reply can be useful
  • Forward UTMs, so you can prove the site beats whatever it replaced
  • Order sections by the decision the buyer actually makes — price comes after the case is made
05

Findable and shareable

The two cheapest, most-forgotten wins. Skip these and the site is invisible to search and ugly in every WhatsApp forward.

  • Canonical URL must point where the site actually answers — never at a domain you have not registered yet
  • A 1200×630 og:image, or every share is a bare text link
  • robots.txt + sitemap.xml + structured data for the local business
  • If a competitor shares the name, disambiguate explicitly or the bigger entity absorbs you
06

Verify on the real device and the real URL

Localhost lies. The traffic is mostly phones, so the CTA has to land on the first screen of a phone — not a laptop.

  • Zero broken images, no horizontal overflow, page scrolls over every section
  • Check the tags on the LIVE url with curl, not on localhost
  • Hard-reload before believing anything is broken
07

Write the handoff before you walk away

Every project gets a note recording the deploy method, what was changed and why, and what is still waiting on the client. Without it, the next session rediscovers the same problems.

  • HANDOFF.md in the repo, plus a copy in the Obsidian vault
  • Record the exact deploy commands that actually work for THAT project
  • List what needs the client, separately from what needs code
⚖️ Standing Rules
Learned the expensive way
Each of these cost real time on a real build. They are non-negotiable now.

Never invent a fact

No made-up prices, hours or testimonials. PENDING degrades to an honest prompt — and the site still ships.

Deploy, then verify the live URL

A green build does not mean the public address updated. Check the live HTML every single time.

Own the media you publish

No Google or Waze imagery, no hotlinked Instagram thumbnails — signed CDN URLs expire within days. Client photos, downloaded and committed.

Consent before faces go public

Any recognisable person needs permission on file. For children it is a legal requirement, not a preference.

Fetch and rebase before editing

More than one agent may be in the repo. Never force-push — keep the other work and re-apply yours on top.

One strong asset beats two weak ones

A weak photo or video next to a strong one drags the strong one down. Cut it rather than filling a grid.
